# Design

## Context

动机见 proposal.md「Why」。现状（出处写在句末）：

- skill 共 7 节：识别、补项目信息、日常巡检、启用判断（可选）、建立 ruff 基线、建立 ESLint 基线、汇报（`skills/rulemason/SKILL.md`，`grep -n "^## " skills/rulemason/SKILL.md`）。开头一句话与 frontmatter description 只说补项目信息、巡检与启用判断（`SKILL.md:3`、`:6`）。
- 「不可违反」一节要求「做之前列出要新增、修改的文件，用户同意后才写」，巡检只报告（`SKILL.md:12-17`）。
- 章节顺序与基线两节的边界由测试钉住：`tests/test_templates.py:117`（各节标题顺序）、`:130`、`:144`（以下一节标题为界切出基线节）。
- 检查点「自动精简」一段只写「重复、死代码、冗余抽象或过复杂逻辑」（`rules/workflow-gates.md`「自动精简与代码审查（apply 后）」一节），主规格对应「Apply 后行为保持的自动精简」，正文 224 字（`openspec show workflow-gates --type spec --json`）。
- 已有能被新章节引用的部分：「改既有测试时」（`rules/workflow-gates.md`）、React「重构等价性」（`rules/react.md`）、ESLint 拆分不卡线与「同时看超过 15 的函数个数」（`lint/eslint-base.mjs`）、「建立 ESLint 基线」的遗留条目（`SKILL.md` 第 6 节）。
- 建议页的经验值（每组 3–6 个文件、并行不超过 9 组、7 个子代理被用量上限打断、7 个辅助函数被复制成 18 份）来自一个接入项目，本机未复现。

## Goals / Non-Goals

**Goals:**
- 用户提出批量清理时，AI 照一份固定流程做，改前证据可信、中断可恢复、不制造新的重复。
- 平时的每一次改动，新函数也先查重。

**Non-Goals:**
- 不加命令、不加配置项，不做自动查重或相似度检测。
- 不规定具体用哪种并行机制（子代理、多会话），流程只写「每组同一份指令」。

## Decisions

1. **存量清理写成 skill 第 7 节，标「可选，用户提出时才做」，「汇报」顺延为第 8 节。** 否决放进 `rules/workflow-gates.md`：检查点是每次改代码都要过的，存量清理是偶尔一次的大活，放进去会让每次改动都读一遍。否决单独一个 skill：流程要引用 skill 已有的「建立 ESLint 基线」与巡检，拆开要跨 skill 引用；且 skill 只住一处的约定里只有一个 `rulemason` skill。
2. **六步只写做法与理由，经验值写成「建议」。** 每组 3–6 个文件、并行组数这类数字依赖工具与用量，写成建议值并说明为什么（太大一组难复核、并行太多易撞用量上限）。否决写成 MUST：别的工具、别的项目规模下不成立。
3. **改前证据一步写明「在改前提交的临时 worktree 上跑，不经 stdin」，并写原因。** 原因是带类型检查的 lint 会按路径读磁盘上的文件，stdin 交进去的内容不会被它分析。否决「改前跑一次存下来」这种不带方法的说法：当时出错就出在方法上。
4. **「先规划共用模块」写进第 1 步规划，并明确不得为缩小改动面要求「不新建文件」。** 否决只在复核时查重：到复核时 18 份已经写出来了，返工比事前规划贵。
5. **检查点「自动精简」加一句「新增函数先按名检索，已有同名或同用途的实现就复用」，只写原则不写命令。** 否决接入 jscpd 等工具进共享基础：只有一个项目提出，且要装 node 依赖；项目可以自己把它写进命令表。否决只写在存量清理一节：平时的改动同样会复制函数。
6. **代理指令只列要点，不给可复制的整段模板。** 要点：只改清单内文件、不动 git 状态、行为等价是硬要求（React 按 react.md「重构等价性」）、碰到源码文本断言按「改既有测试时」、汇报格式。否决整段模板：要按项目语言和工具改写，整段照抄反而容易漏改。

## Risks / Trade-offs

- [skill 变长，日常巡检时 AI 也会读到这一节] → 节标题写明「可选，用户提出时才做」，与第 4 节同一写法；正文控制在 30 行以内。
- [按名检索查重只能找到同名的，换了名字的重复找不到] → 「同用途」靠精简时人眼判断；规矩第 7 条本来就要求，检查点只是提醒先查。
- [临时 worktree 需要装依赖才能跑 lint] → 步骤里写明可以复用本机缓存离线安装，装不上时说明并改用 git 取文件后在同一配置下跑的替代做法由用户决定。
- [共享正文改动影响所有接入项目] → 只加一句与一节，`update` 后生效；本仓库测试钉住章节顺序与关键措辞。

## Migration Plan

1. 改 `skills/rulemason/SKILL.md`、`rules/workflow-gates.md`、`tests/test_templates.py`，跑 ruff 与测试。
2. 在一个接入项目运行 `rulemason update`（不提交），确认副本只多这一节与一句、`check` 一致。
3. 发版，发布说明写明新章节与查重一句。

回滚：`uv tool install rulemason==<上一版>` 后在接入项目 `rulemason update`，副本回到旧文字；不改任何文件格式。

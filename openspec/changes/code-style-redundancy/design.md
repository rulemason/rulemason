# Design

## Context

动机见 proposal.md「Why」，要求见 `specs/shared-code-style/spec.md`。现状（出处写在句末）：

- 第 8 条已经比较长，管兜底只放在最外层、不吞异常、不静默改走另一条路径（`rules/code-style.md:12`）。第 9 条只有一句：「不加当前没有调用方的参数、配置项、扩展点。」（`rules/code-style.md:13`）
- React 落法逐条写了九条在 React 里的写法，第 9 条是「不加当前没有调用方的 props、变体或配置」（`rules/react.md:17`）。Python 落法没有逐条对应的列表，只写 Python 特有的约定（`rules/python.md:3-11`）。
- 「九条」这个名字和编号被这些地方引用：
  - 测试断言九条正好 9 条（`tests/test_templates.py:354`），第 8 条含「静默改走另一条路径」（`tests/test_templates.py:385-386`）；
  - ruff 与 ESLint 基础配置的注释按条号写（`lint/ruff-base.toml:9-14`、`lint/eslint-base.mjs:5`）；
  - skill 的加载自测问「九条第 9 条是什么」（`skills/rulemason/SKILL.md:52`）；
  - 独立审查按九条检查代码质量（`rules/workflow-gates.md:51`）。
- 自动精简处理的是「重复、死代码、冗余抽象或过复杂逻辑」（`rules/workflow-gates.md:40`），但九条里没有对「冗余抽象」的定义，审查和精简各自理解。
- ruff 基础配置没有启用 `ARG`（未用参数）（`lint/ruff-base.toml:7-20`）。

## Goals / Non-Goals

**Goals:**
- 独立审查和自动精简都能指着九条的原文，报出三类冗余。
- 措辞要分得清「该内联的抽象层」和「为降复杂度拆出的辅助函数」，不让 AI 为了守第 9 条把拆好的函数又并回去。

**Non-Goals:**
- 不让检查点回头修既有代码：检查点只审本次 diff，存量问题交给后续的 `cleanup-mode`。
- 不改 `src/rulemason/` 的代码，也不改发布与副本机制。

## Decisions

1. **并进第 8、9 条，不新增第十条。** 否决新增「第 10 条」：要改 skill、测试、lint 注释，还有 README 里所有「九条」的说法，而且新条会和第 9 条重叠。否决放进「九条之外」：那一节只放和具体某条无关的通用约定，这三类分别是第 8、9 条在同一方向上的延伸。
2. **防御性重复检查放第 8 条。** 第 8 条的主题是「错误处理放在哪一层、不掩盖」，重复检查和多余的 `try` 都属于错误处理放错了层。否决放第 3 条：第 3 条要求给看不出原因的分支写注释，把「别写这个分支」也放进去，同一条就既要求写又要求删，读者会混淆。
3. **以「自身有没有逻辑」区分要内联的抽象层。** 内联对象只限只转发参数的包装函数、只有一个实现的基类或接口、只为一处调用建的工厂或策略类；带自己逻辑的辅助函数即使只有一个调用方也不算。否决「只有一个调用方的函数一律内联」：这和复杂度上限（C901、`complexity`）冲突，复杂函数本来就要拆成只被调用一次的辅助函数；也和第 2 条的分步骤写法冲突。否决按行数划线（比如少于 3 行就内联）：短函数也可能是有意义的命名，行数说明不了它是不是只做转发。
4. **看不出上游保证时不删检查。** 判断依据只认调用链里看得到的校验或类型声明，看不出来时改为按第 3 条写注释。否决「内部函数一律不做参数检查」：这会让 AI 在看不清调用链时也删检查，把能拦住的错误放进去。
5. **不加 lint 规则。** 否决把 `ARG` 加进 ruff 基础配置：所有接入项目升级后都会新增一批既有问题，要重建基线，而这个 change 只想改措辞。否决引入 vulture 之类的死代码工具：这是新依赖，误报要靠项目写白名单。诊断时临时启用这类规则的做法放进 `cleanup-mode`。
6. **React 落法只同步第 9 条。** React 里冗余抽象的典型样子是只转发 props 的包装组件，值得单独写一句。第 8 条的通用措辞已经能覆盖可选链 `?.` 之类的重复检查，落法只写 React 特有的形态。Python 落法没有逐条列表，不改。

## Risks / Trade-offs

- [AI 误判「上游已保证」，删掉了必要的检查] → 规则只认看得到的校验或类型声明，看不出就保留；规格里有对应场景，独立审查可以按场景核对。
- [新第 9 条与第 7 条「出现第二次就抽函数」互相拉扯] → 第 7 条管出现两次以上的逻辑，第 9 条管只有一个调用方、又不带逻辑的抽象，两者处理的对象不同；规格里「为降复杂度拆出的辅助函数」场景确认两条不冲突。
- [第 8 条更长，读的人难抓重点] → 只加一句，放在条末，不改原有半句的顺序；测试仍能按原文断言。
- [接入项目升级后，审查开始报既有代码里的这三类问题] → 检查点只审本次 diff，既有代码不受影响；发布说明写明存量清理另有入口。
- [加载自测「九条第 9 条是什么」的标准答案变了] → 自测只看工具能不能答出副本里的原文，答出新措辞就算通过，不用改 skill。

## Migration Plan

1. 本仓库改 `rules/code-style.md` 和 `rules/react.md`，补测试，运行 `uv run ruff check .` 和 `uv run pytest`。
2. 按额外步骤，在接入项目运行开发版 `rulemason update --dry-run`，确认只刷新规则副本和 `.rulemason.yaml`，不提交也不推送。
3. 发版时版本号按 PyPI 上已有的版本递增，发布说明写明第 8、9 条的新措辞。接入项目运行 `uv tool upgrade rulemason` 和 `rulemason update`。

回滚：发布上一个版本后，接入项目运行 `uv tool install rulemason==<上一版>` 再 `rulemason update`，规则副本即恢复原措辞。这次不改项目自己的文件，所以不需要手动清理。

# Design

## Context

动机见 proposal.md「Why」，要求见 `specs/rules-layer-setup/spec.md`。现状（出处写在句末）：

- skill 只有一个，ID 是 `rulemason`（`skills/rulemason/SKILL.md:2`）。`/rulemason:cleanup` 是插件命名空间，项目 skill 没有这种写法。
- 第 7 节「存量清理」是六步：规划、先存证据、代理指令、恢复、主会话复核、收尾（`skills/rulemason/SKILL.md:137-146`）。要用户先点名一类违规才进入。测试要求这一节不超过 30 行（`tests/test_templates.py:171`）。
- 第 1 节用 `next.code` 决定做哪一阶段（`skills/rulemason/SKILL.md:23-33`）。「一次只做一件事」要求先列文件、用户同意后再写（`skills/rulemason/SKILL.md:13`）。skill 不提交（`skills/rulemason/SKILL.md:16`、`:146`）。
- `.rulemason/` 是 `init` / `update` 生成的只读副本，手改由 `check` 发现（`AGENTS.md:3`）。
- ruff 基础 `select` 有 `ERA001`、`T201`、`BLE001`，没有 `ARG`、`S110`（`lint/ruff-base.toml:7-20`）。本机 `ruff 0.17.3` 认识这两条：`uv run ruff rule ARG001` 与 `uv run ruff rule S110` 退出码都是 0。
- 九条第 8、9 条已经写进三类冗余（`rules/code-style.md:12-13`）。检查点只修本次改动引入的问题（`rules/workflow-gates.md:29`）。
- jscpd 与 pylint 要钉的具体版本号未核实，实现时再查当时的稳定版。

## Goals / Non-Goals

**Goals:**

- 用户不带模块名就能得到全仓排序：每个模块都有硬指标、机械软指标和一档精简潜力。
- 带模块名只修该模块，且仍然先确认再改。
- 两次诊断的进度可比：不靠上一份诊断稿。

**Non-Goals:**

- 不改检查点，让它回头修既有代码。
- 不把查重工具或 `ARG` 写进项目依赖和 lint 基础配置。

## Decisions

1. **给现有 skill 加用法，不新开 skill。** 用户输入 `cleanup`，或用自然语言说要做存量清理，都进第 7 节。否决插件写法 `/rulemason:cleanup`：分发进去的是单个项目 skill，不是插件。否决再做一个 `rulemason-cleanup`：要改分发清单，还得跨 skill 引用第 5、6 节和现有六步。
2. **`next.code` 只做入口闸门。** `init`、`fix_manifest`、`upgrade_machine`、`update` 停下；`fill_project_info`、`manual_lint`、`fix_gitignore`、`none` 继续。否决清理也去排队等「补项目信息」：简介没写完不影响读代码。否决 `update` 时照样诊断：副本和 lint 配置还不是这一版，数字对不上。
3. **诊断分三层，不全仓通读。** 硬指标读「接入前遗留」条目和复杂度；机械软指标全仓统计；每个模块只抽 2 到 3 个最大或最复杂的文件，给高/中/低和 1 到 2 个例子。修模块时才通读该模块。否决全仓通读软建议：同一仓库读两遍，条数会变，用户无法拿它当进度，也容易碰到用量上限。否决诊断只列硬指标：软建议才是精简的主要来源，至少要有全仓的机械部分和抽样。
4. **查重用到时再跑，版本写死在 skill 正文。** 有 Node 用 `npx --yes jscpd@<版本>`，否则对 Python 用 `uvx pylint@<版本> --disable=all --enable=duplicate-code`，离线或下载失败就空出这一列。否决装 rulemason 时顺带安装：Python 包没有装完后的钩子，也碰不到 npm。否决 `init` 写入项目依赖：`init` 只写标记块和基础配置。
5. **进度不落文件。** 硬指标看遗留条目还在不在；软指标看 `git log` 里 `refactor(cleanup): <模块>`。skill 仍不提交，收尾只告诉用户提交说明怎么写。否决写进 `.rulemason/`：副本是只读的，`check` 会报手改。否决在仓库里加状态文件：多一个要提交、而且会过期的产物。
6. **并行分开封顶：诊断最多 5 个只读代理，修模块最多 3 个会写文件的代理。** 没有子代理就串行。否决诊断和修复用同一个数：修复会改文件，同时写太多难复核。否决不写死数字：现有第 7 节只说「按用量上限定」，各次会话宽严不一。
7. **模块名只划定范围，不是同意。** 先列出计划和要落地的建议，用户确认后才改；用户可以只同意其中几条。否决带上模块名就直接改：和第 7 节现有的「用户确认后再做」、以及「一次只做一件事」冲突。
8. **仍写在第 7 节，测试的行数上限从 30 调到 70。** 否决新开第 9 节：汇报固定是第 8 节，测试按「第 7 节到第 8 节」截取。70 行盖住入口、三层和原六步；写超了再说明，不预先放得更宽。
9. **`ARG` 与 `S110` 只在诊断时用临时参数打开。** `ERA`、`BLE`、`T201` 已经在基础 select 里，但按文件的遗留豁免会把它们从日常 ruff 里藏住，所以硬指标层读豁免条目，机械层再用临时 `--select` 统计这五条。否决把 `ARG` 加进 `lint/ruff-base.toml`：所有接入项目会多出一批既有问题，要重建基线。

## Risks / Trade-offs

- [抽样的精简潜力两次诊断档位不同] → 档位只用来排序，不拿条数当进度；进度只认遗留条目和提交说明。
- [查重工具下载失败或离线] → 空出该列并写明原因，其余两层照常。
- [用户以为带了模块名就已经同意修改] → 规格要求先列计划，未确认不改文件；测试断言这句还在。
- [几个代理同时改到同一文件] → 沿用「同一文件只属一组」，写文件的代理最多 3 个。
- [第 7 节变长，读的人抓不住] → 入口、诊断、六步分段写；行数上限 70，超出一倍要在汇报里说明。
- [用户不按约定写提交说明，软进度看不出来] → 收尾写明那一行提交说明；没提交就在下次诊断里标明这个模块还没有清理提交。

## Migration Plan

1. 本仓库改 skill 与测试，按检查点收尾后发版。发布说明只写存量清理的新用法，不改九条。
2. 接入项目运行 `uv tool upgrade rulemason`，再 `rulemason update`，按各项目惯例提交副本。
3. 回滚：再发一版，把第 7 节和测试恢复成上一版。PyPI 上已发出的版本不能删，只能再发。没有要迁移的数据或状态文件。

# Design

## Context

动机见 proposal.md「Why」。现状：

- `rules/workflow-gates.md` 两处要求 ruff「修掉报出的问题后重跑，直到通过」：apply 后第 2 步、直接改动第 4 步。没有区分问题是本次引入的还是本来就有的。
- `skills/rulemason/SKILL.md` 补项目信息第 6 步只运行 ruff，把问题列进汇报，「不自动修代码」；日常巡检一节写明只读、不改文件。
- 共享基础配置 `lint/ruff-base.toml` 在 `"B"` 一行已注明：框架约定在参数默认值里调函数的，由项目用 `extend-immutable-calls` 声明。目前没有任何地方替用户做这一步。
- `src/rulemason/templates/AGENTS.md.tmpl` 同时写「## 红线（不可违反）」一节与命令表下方「红线规则：暂无。」一行；`rules/workflow-gates.md` 第 5 行把「红线规则」定义为项目在同处列出的实质类规则。

## Goals / Non-Goals

**Goals:**
- 有大量既有问题的项目，建立基线后 ruff 能通过，此后检查点只管本次改动。
- 豁免全部写在项目的 ruff 配置里，看得见、能逐步清掉；自动修复只动用户确认的文件。

**Non-Goals:**
- 不加命令行功能（用户决定先用 skill 方式，实际用过后再评估）。
- 不处理 ESLint 的既有问题。

## Decisions

1. **基线用按文件的 `per-file-ignores` 记录，原因写「接入前遗留，改到该文件时清掉」。** 否决 `# noqa` 逐行豁免：python.md 规定豁免写在 ruff 配置里、不逐行加 noqa；否决按目录豁免：同目录里没碰过的文件以后新出的问题也会被放过；否决在项目里关掉整条规则：新代码也不再受约束。
2. **分类统计与写配置由 skill 指导 AI 完成。** 否决给 `rulemason check` 加基线输出：用户已决定先用 skill，在真实项目跑过、确认分类有用后再考虑做成命令。
3. **自动修复只做 `I001` 与 `F401`，排除 `__init__.py`，先给命令与数量，确认后才运行。** 这两类 ruff 标为安全修复，量大且改法机械。否决 `ruff check --fix` 全量：会连带其他规则的修复，范围不可预期；否决 `--unsafe-fixes`：可能改变行为；排除 `__init__.py` 是因为其中的未用导入常是有意的再导出。
4. **框架写法在项目 ruff 配置声明 `extend-immutable-calls`。** 依赖里有 `fastapi` 时列 `fastapi.Depends`、`Query`、`Path`、`Body`、`Header`、`Cookie`、`Form`、`File`、`Security`；有 `typer` 时列 `typer.Option`、`typer.Argument`。否决写进共享基础配置：基础配置保持与框架无关，这是它注释里已定的取舍；否决对 B008 加 `per-file-ignores`：会把真正的可变默认值问题一起放过。
5. **检查点按「问题落在本次 diff 改动的行上」判断是否本次引入。** 照常运行命令表的 ruff，只修落在新增或修改行上的问题；新加的 import 未被使用、因本次改动在未改的行上新出现的问题（如 C901 报在 `def` 行、I001 报在 import 块首行）也算本次引入。否决 `git stash` 后对比前后两次运行：会动用户未提交的改动；否决只看问题总数是否增加：看不出是哪几处，也修不准。
6. **新项目模板改写「判断用的红线规则」，检查点里「红线规则」的定义改为「命令表之后列出、供判断使用的实质类规则」。** 新旧两种写法都能被这条定义覆盖，已接入项目不必改。否决把项目那一节改名：「红线」是给人看的说法，用户已经熟悉；否决让 update 改写已接入项目的这一行：它在标记块外，属于项目内容。
7. **日常巡检放开「只读」的唯一例外：用户确认的基线计划。** 否决只在补项目信息时做基线：已经补完信息的项目（如问题报告里的 monorepo）就永远建不了基线。

## Risks / Trade-offs

- [`per-file-ignores` 一次写进几百个文件，配置很长] → 按路径排序、每个文件一行；汇报写明条目数，后续改到哪个文件清哪个。
- [`F401` 修复删掉 `__init__.py` 以外的有意导入] → 修复后先跑测试再提交，建议单独一个提交，出问题整体撤回。
- [按改动行判断时，搬动整段代码会把旧问题带进改动行] → 搬动的代码按既有问题处理，汇报写明是搬动带来的，修不修由用户决定。
- [依赖识别漏掉框架（用别名或间接依赖）] → 计划里列出 B008 的数量与所在函数调用，用户可以补充要声明的函数。
- [已接入项目保留旧写法「红线规则：暂无。」] → 新定义同时覆盖新旧写法；巡检时可提一句可以改，不强制。
- [按文件豁免后，遗留文件里新写出的同类问题被放过（例如再写一个裸 `except`）] → 检查点汇报会提醒该文件还有遗留豁免、可以顺手清掉；改到遗留文件时可加跑 `ruff check <文件> --config "lint.per-file-ignores = {}"` 看改动行；是否把这一步写成强制，等真实项目用过后再定。
- [`ruff --fix` 改到用户未提交的文件] → 计划里先用 `--diff` 列出会改的文件并与 `git status` 对照，有重叠时请用户先提交或排除。

## Migration Plan

1. 本仓库改共享正文、skill 与模板，跑测试；在问题报告里的 monorepo（或照它搭的临时项目）按新 skill 走一遍基线，记录前后问题数。
2. 发版（版本号按发版时 PyPI 已有版本递增），接入项目运行 `uv tool upgrade rulemason` 与 `rulemason update` 拿到新检查点副本。
3. 有既有问题的项目运行一次 `/rulemason` 建立基线。

回滚：项目里的基线只是 ruff 配置与一次自动修复提交，用 git 撤回即可；检查点正文与 skill 回到上一版本只需 `uv tool install rulemason==<上一版>` 后 `rulemason update`。

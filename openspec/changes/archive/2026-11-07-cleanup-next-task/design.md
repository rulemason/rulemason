# Design

## Context

动机见 proposal.md「Why」。现状：

- 不带模块名时，队列之后的最后一行是 `/rulemason cleanup <模块>`（`skills/rulemason/SKILL.md:145`）。每个模块抽 2 到 3 个文件，并举 1 到 2 个例子（`skills/rulemason/SKILL.md:153`，`openspec/specs/rules-layer-setup/spec.md:338`）。
- 修完一个模块的收尾按同一顺序重算下一个，不再抽样，也不看高、中、低（`skills/rulemason/SKILL.md:164`，`openspec/specs/rules-layer-setup/spec.md:388`）。
- 第 7 节测试要求不超过 70 行（`tests/test_templates.py:171`）。当前这一节是 26 行（`skills/rulemason/SKILL.md:139-164`）。

## Goals / Non-Goals

**Goals:**

- 用户在输入下一条命令之前，能看到这次要动哪里、做什么。
- 这句话来自已经抽过的例子，收尾不为它再读文件。

**Non-Goals:**

- 不把进入模块后的文件分组计划提前到诊断。
- 不改队列排序，也不保存这句话。

## Decisions

1. **命令前加一句，材料只用该模块已有的 1 到 2 个例子。** 写明要动的位置、要做的事，以及软指标里哪一类不算这次要清的内容。最后一行仍是命令。否决在诊断里列出文件分组计划：分组要等进入模块后通读，诊断只有抽样，两份计划会对不上。
2. **这一句只接到现在要进入的那一条命令上。** 队列其余行不写。否决每一行都写一句：用户要的是下一步，各模块的例子已经在抽样里。
3. **这句不是计划，也不是确认。** 用户输入命令后仍先通读、列计划、等确认。否决把这句当成可以开工的清单：抽样没覆盖整个模块。
4. **收尾不重新抽样。** 同一次诊断的抽样里已经有下一模块的例子时，用那些例子写成同样的一句，放在下一条命令前。没有这些例子时只给命令或要先提交的路径。否决只重复刚做完那个模块的一句：那句说的是已经做完的模块。否决把这句话写入文件：下次会话的例子会变，写了也会过期。

## Risks / Trade-offs

- [抽样例子和进入后的计划不一致] → 进入后通读重列计划，这一句只指出方向。
- [收尾在新会话里写不出具体任务] → 只给命令或要先提交的路径，并写明具体改哪些等进入模块后的计划。
- [第 7 节超过 70 行] → 预计增加约 4 行，现为 26 行；超出再在汇报里说明，不预先放宽上限。
- [条数最多的一类不是这次要清的内容] → 这一句写明哪一类不算这次要清的内容。

## Migration Plan

1. 本仓库改 skill 与测试，按检查点收尾后发版。发布说明只写：清理命令前用已有例子写明这次要做的事。
2. 接入项目运行 `uv tool upgrade rulemason`，再 `rulemason update`。本机若被精确版本钉住，改用 `uv tool install rulemason@latest`。
3. 回滚：再发一版，把第 7 节和测试恢复成上一版。PyPI 上已发出的版本不能删。没有要迁移的任务文件。

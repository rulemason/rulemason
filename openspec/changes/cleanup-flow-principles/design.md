## Context

动机见 proposal.md「Why」。与做法相关的现状：

- `skills/rulemason/cleanup.md` 现为 28 行（`wc -l skills/rulemason/cleanup.md`），结构是：入口、只诊断与队列、完成标记、诊断三层、修一个模块的 1–6 步。0.8.39 起由 `SKILL_FILES`（`src/rulemason/shared.py:46`）复制到各工具 skill 目录，只在做存量清理时读，不计入常驻规则字数。
- `tests/test_templates.py` 的 `test_skill_legacy_cleanup_section` 断言 `cleanup.md` 不超过 70 行，并逐字断言约 90 个短语（如 `git worktree add --detach`、`临时目录放在仓库外`、`不把诊断或进度写入 \`.rulemason/\``）。其中不含「拆函数拆到下一档以内」。
- 九条之外已有「重构时不改、不搬别处按名字或原文依赖的东西」（`rules/code-style.md`，0.8.38），React「重构等价性」已有依赖数组与同位置换组件两条（`rules/react.md`）。`cleanup.md` 只需引用，不重复写。
- 要落地的反馈条目与判断见 Notion 审阅子页「审阅：59 条反馈逐条判断与浓缩方案」第二、三节（第 4、16、19–25、27、36、37、41–45、47、49–52、55–57、59 条）；复杂度探针（第 7、13、26、39 条）与 knip（第 40 条）不在本次。
- 主规格 `rules-layer-setup` 的「存量清理按固定流程做」写死了改前证据在临时 worktree 上跑；「诊断分三层且不另存进度」禁止新的状态文件。两条都与本次放宽冲突，用 MODIFIED 改。

## Goals / Non-Goals

**Goals:**

- 原则在前、做法在后：每条新加的具体做法都能对应到七条原则之一。
- 测试已断言的短语全部保留，只增不删。

**Non-Goals:**

- 不改诊断排序、完成标记与收尾选下一个模块的规则（上一版刚修过）。
- 不写任何新的命令或附带文件。

## Decisions

1. **原则放在 `cleanup.md` 开头，做法写回各步**。否决：单独一节「经验清单」逐条列反馈。逐条列会把 40 条原样搬进来，正是浓缩方案要避免的；写回各步，代理在走到那一步时读到。
2. **改前证据默认在当前工作区取，worktree 只作补取用**。否决：一律建 worktree（反馈第 25 条：清单文件无未提交改动时，动手前的工作区就是改前状态，建 worktree 还要重装依赖）；也否决完全去掉 worktree，动手之后才发现要多盯的指标仍需要它。测试断言的 `git worktree add --detach`、`git worktree remove --force` 因此保留。
3. **工作笔记只许放仓库外，且不当作进度来源**。否决：允许写进仓库（如 `.rulemason/`），那会变成要提交、要巡检的状态文件。进度仍只看遗留条目与 `refactor(cleanup):` 提交。
4. **复杂度目标做成计划里二选一，不再在代理指令里写死「拆到下一档以内」**。否决：保留写死。常同步上游的分支拆得越深冲突越多（反馈第 16 条），这是项目的取舍，应由用户在计划里定。
5. **「项目保留全局上限」只报告，不劝删**。否决：照旧口径要求删掉全局上限改按文件基线。上一次审阅已定：不认可全局分档为对等选项，但项目坚持时只报实测数。
6. **等价证据写成推荐做法，不设数量要求**。否决：给变异检查定配额（反馈第 42 条要求「全部被发现」）。不同模块能做的对跑差别很大；硬性数量会逼出凑数的植入。写成「对跑测试写好后先植入改动确认它会失败」，和编码审慎第 5 条同理。

## 措辞草稿

开头七条原则（实现时可调用词，含义不变）：

1. 别处按名字或原文依赖的东西不动（见 code-style 九条之外）。
2. 等价的证据要独立于「测试通过」；对跑测试写好后，先植入一处改动看它失败。
3. 指标是手段：指标变好而读者没得到好处，就放弃这一处。
4. lint 因重构要求改语义时（如要求改依赖数组），放弃这处重构，不去满足 lint。
5. 代理只改清单内的东西，行为差异逐项写进汇报。
6. 状态以 git 为准；笔记写明提交号。
7. 改前改后用同一条命令、同一组参数、同一个范围对比。

## Risks / Trade-offs

- [`cleanup.md` 变长后接近 70 行上限] → 原则每条一行、做法并进已有句子；超出时先合并句子，不调高上限。
- [代理把「工作笔记可放仓库外」读成可以不看 git] → 规格与正文都写明笔记不是进度来源，接着做之前先用当前提交核对。
- [复杂度目标交给用户选后，计划多一个问题] → 计划里给出推荐项与理由（是否常同步上游），用户可以直接同意。
- [「放弃靠透传大量参数的拆分」没有数字门槛，代理理解不一] → 要求汇报写明放弃的位置与当前复杂度，由主会话判断；不设数字，免得变成新的指标。

## Migration Plan

1. 本仓库合并本 change，发补丁版本。
2. 接入项目升级本机 rulemason 后运行 `rulemason update`，两份工具目录下的 `cleanup.md` 随之刷新；只影响做存量清理时的流程。
3. 按 AGENTS.md「额外步骤」，在一个接入项目用开发版只读运行 `rulemason update --dry-run` 与 `rulemason check`。

回滚：还原本 change 的提交并发补丁版本；接入项目再运行 `rulemason update` 即恢复旧正文。

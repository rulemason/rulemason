01

The code gets hard to read

rulemason is a set of rules for AI coding tools, plus a checkpoint after every change. It supports Claude Code, Cursor, Codex, and OpenCode. The rules live in the project. The AI follows them when it writes plans, code, and docs.

  • 01Duplication

    The same logic is copied several times. After each change, the AI first removes duplication in that change. The requirements and the observable behavior stay the same.

  • 02Dead code

    Functions and parameters nobody calls stay where they are, and “we might need this later” adds another layer of abstraction. Logic that appears a second time is extracted into a function. Unused parameters and functions are not left behind.

  • 03Hard to read

    As features pile up, the syntax gets more complicated, and even the engineers struggle to read it. Bugs are hard to trace, and the result is awkward to turn into material you would show someone else.

02

Read, keep, check

Put the rules in the project, follow them while writing, then pass the checkpoints. Checkpoints that involve plans and code need OpenSpec (npm install -g @fission-ai/openspec@latest). Without it, rulemason still installs the rules and lint setup. Run rulemason update after OpenSpec is installed to fill in the checkpoints.

Read the project rules first

rulemason init writes only the files in the plan. It does not commit or push. At the end it prints the check result, the files it changed, and the next step. Then run /rulemason once inside the AI tool: check the project summary, and confirm the red lines and the command table.

The rules are maintained in one place. Every tool reads the same read-only copy, committed with the project. Teammates, cloud agents, and CI can read them without installing rulemason.

Keep plans and code to the rules

On the OpenSpec path the AI runs the checkpoints from the rules. The plan is checked when it is written and again before code. The plan is sent to Jev only when a key is set. With no key, Jev is not called. The design-doc format check runs locally, and the remaining rules are left for a person. rulemason judge --change <name> --lint-only checks format only and does not use the network.

The nine writing rules apply throughout. Examples: the first line of each file says what the file is for, the main flow is commented step by step, and errors are not swallowed inside the program. Python is checked with ruff. React is checked with ESLint. PRDs, plans, and specs state what this change will not do, write down the rejected alternative for each decision, pair each risk with a mitigation, and say how a rollout rolls back.

The copy check runs when UI copy changed and judgment is enabled. Banned phrases and short labels are checked locally. Longer copy is sent to Jev only when a key is set. Without judgment it is skipped, and the report says the judgment layer is not installed (判断层未装).

Check lint, tests, and review

After the code is written, the checkpoints have the AI simplify duplication, dead code, extra abstraction, and roundabout logic in that change, ask an independent reviewer to read it, then run ruff and tests. Must-fix issues, and comments that can be fixed safely inside the change, are fixed and reviewed again, for at most two rounds. If a must-fix issue is still there after that, the work stops and the remaining items are reported.

The reviewer gets no files and no commands. It only sees the change and the plan it was given, and it reports on six points: requirements, correctness, security, code quality, tests, and whether the diff is clean. Only problems introduced by this change are fixed. Problems that were already there are counted and left alone. On Claude Code, simplify uses its built-in /simplify.

If a rule copy is edited, a tool entry point is missing, or lint does not extend the base rules, rulemason check exits non-zero, so CI can block it. If the recorded version is older and the copy contents match, the exit code stays 0.

How it works

Built-in rules apply throughout. Jev runs only when a key is set. With no key, Jev is not called.

  1. Built-in rules

    • Python / React guides
      Three copy tiers, copied per project
    • Plan-writing rules, coding caution
      Product-artifact caution, prose hygiene
      CJK typography

  2. Plan

    1. /opsx:propose
      Write the plan

    2. Judge the plan
      Jev only with a key

    • Red lineStop and ask you.
    • Pass/opsx:apply checks again before code. Jev only with a key.
    • No keyJev is not called. Local format check; the rest is manual. --lint-only is format only.

  3. Write code and check it

    1. Write code

    2. Simplify

    3. Independent review

    4. ruff

    5. Tests

  4. Finish and archive

    1. Frontend lint

    2. Copy check
      Needs judgment. Long copy uses Jev only with a key.

    3. Write verification.md

    4. /opsx:archive

  • Simplify touches only this change. Requirements, observable behavior, and APIs stay the same.
  • Independent review runs for at most two rounds. If a must-fix issue remains, the work stops and the remaining items are reported. You are not asked to review the code line by line.
  • Small edits outside OpenSpec: if the project has openspec/, the AI reads the main specs first. A change that would break a promised behavior stops and asks you. Anything else is edited directly, then ruff and tests run. Neither path simplifies, runs the independent review, or writes verification.md.

06

Designed so you can trust it

  • Look before it writes. init and remove list the files first and write only after you confirm. update refreshes the copies and entry points it owns immediately. For your own files (ruff, ESLint, openspec/config.yaml, and the like), a missing setting is listed in a fill-in plan and written only after you confirm. --plan and --dry-run only print the plan.
  • It does not commit or push. The changes stay in the worktree for you to review.
  • It does not force your config. If a ruff config sets select, extends a file outside the project, or the ESLint config is in a form it cannot read, it reports the file, the line, the original text, and what to change.
  • An existing project does not go red on day one. Run /rulemason to set a baseline. Nothing is written until you confirm. After that, checkpoints fix only problems the new change introduces. No rule is switched off globally, and the global complexity cap is not raised.
  • CI can block it. If a rule copy is edited, a tool entry point is missing, or lint does not extend the base rules, rulemason check exits non-zero. If the recorded version is older and the copy contents match, the exit code stays 0.
  • Secrets stay out of the chat. rulemason key reads the key in your own terminal, does not echo it, and does not put it in shell history. It is stored in ~/.config/rulemason/env on this machine (mode 600 on POSIX) and is never committed. The environment variable TYPESAFE_API_KEY takes priority over that file.
  • You can remove it. rulemason remove --plan shows what would be deleted and changes nothing. A copy you edited, so it no longer matches the recorded checksum, is kept and listed. The project summary, red lines, and command table stay in AGENTS.md.

07

FAQ

How is this different from writing AGENTS.md or CLAUDE.md myself?

A hand-written rule file is a prompt. The AI might follow it, and it might not, and nobody notices if it is edited. rulemason adds three things: the rules are maintained in one place and every tool reads the same copy; finished code goes through a fixed set of checkpoints; rulemason check can fail CI when a copy is edited or an entry point is missing. Your own text still lives outside the markers.

How does it relate to OpenSpec?

OpenSpec is how a plan is written and carried out step by step. rulemason is which rules to follow while writing, and which checkpoints to pass when the writing is done. rulemason adds the plan-writing rules to openspec/config.yaml and attaches the checkpoints to apply and archive. Without OpenSpec, you get the rules and lint setup only.

Does it conflict with workflow plugins such as superpowers or get-shit-done (GSD)?

They focus on different things. Those plugins mainly tell the AI how to plan and carry out a task. rulemason mainly says what the code and docs should look like, and how to check them after they are written. The rules are committed with the project, so CI can check them.

Will it damage my project?

init writes only the files in the plan, and it does not commit or push. Lint config it cannot rewrite is reported, not forced. To look first, run rulemason init --plan. To leave, run rulemason remove --plan and read what would be deleted.

Does it need a network? Does it cost money?

The rules, the checkpoints, check, result-check, and judge --lint-only all run on your machine. Only Jev judgment calls TypeSafe over the network, and the key comes from typesafe.ai. Pricing is whatever that site says at the time.

Can I use it if I do not read Chinese?

The command-line output, the generated rules, and the skill are written in Chinese. This page is the English version of the Chinese page. The output you see while using it is still Chinese.

Can it file a software copyright or a patent for me?

No, and it does not guarantee that any application will be approved. What it can do is keep the code concise, the structure clear, and the comments in place, with a check record for each change. Those make the filing materials easier to prepare.

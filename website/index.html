AI CODING, WITH RULES

AI 写代码，
也讲章法。

让 AI 写的代码，读起来像人写的。

用 AI 写代码很快，难的是几个月以后。功能一个个加上去，代码越堆越多：同一段逻辑复制了好几份，没人调用的函数和参数留在原处，读起来完全不像人写的代码。

uv tool install rulemason
rulemason init

需要 uv，Python 3.11 或更高。在项目根目录运行 rulemason init：勾选你用的 AI 工具，看一眼计划，确认后写入。终端不能提问时：rulemason init --tools claude,cursor --yes。工具 id 是 opencode、claude、cursor、codex。

项目一大，代码就难读

rulemason 是给 AI 编码工具定的一套规矩，外加每次改动都要过的关卡。支持 Claude Code、Cursor、Codex、OpenCode。规矩写在项目里，AI 写方案、写代码、写文档时照着做。

  • 01重复

    同一段逻辑复制了好几份。每次写完，AI 先把这次改动里的重复精简掉，需求和对外行为保持不变。

  • 02死代码

    没人调用的函数和参数留在原处，为了「以后可能用到」套了一层又一层抽象。同一段逻辑出现第二次就抽成函数，不留没人调用的参数和函数。

  • 03难读

    功能加上去以后，语法越来越复杂，连工程师自己都很难看懂。出了问题不好查，想整理成材料拿出去也拿不出手。

读、守、查

先把规矩放进项目，写的时候照着守，写完再过关卡。方案和代码的关卡需要 OpenSpec（npm install -g @fission-ai/openspec@latest）。没装也能先接入规矩和 lint，装好后运行 rulemason update 补齐。

读 先读项目规则

rulemason init 只写计划里列出的文件，不提交、不推送。结尾会给出 check 的结论、这次改了哪些文件，以及下一步。然后在 AI 工具里运行一次 /rulemason，核对项目简介、确认红线和命令表。

规矩只在一处维护。每个工具读同一份只读副本，副本随项目提交。同事、云端 agent 和 CI 不装 rulemason 也能读到。

守 方案与代码守约定

走 OpenSpec 时，关卡由 AI 按规矩执行。方案写完、写代码前各查一次。有 key 才把方案交给 Jev；没有 key 时不调用 Jev，设计文档的格式在本机检查，其余规则记为待人工。rulemason judge --change 功能名 --lint-only 只查格式，不联网。

九条写法规矩全程生效。例如每个文件第一行写它是干什么的，主流程按步骤写注释，错误不在内部被悄悄吞掉。Python 由 ruff 检查，React 由 ESLint 检查。PRD、方案、规格要写「这次不做什么」，每个决策要写被否决的备选，风险要写对策，上线要写回滚方式。

改了界面文案、并且已经开启判断时，才检查套话和中文排版。禁词和短标签在本机查；较长的文案有 key 才交给 Jev。没开判断就跳过，汇报里写明「判断层未装」。

查 lint、测试、审查

写完代码，关卡会让 AI 先精简这次改动里的重复、死代码、多余的抽象和绕弯的逻辑，再请一个独立的审查者看一遍，然后跑 ruff 和测试。必须修的问题，以及改动范围内能安全修的意见，会自动修好再审，最多两轮。两轮后还有必须修的，就停下来说明。

审查者拿不到文件和命令，只看交给它的改动和方案，从需求符合、正确性、安全、代码质量、测试、改动是否干净六个方面给出结论。只修这次改动新引入的问题；改动前就有的问题列出数量，不顺手乱改。Claude Code 里精简这一步用它自带的 /simplify。

规矩副本被改、工具入口缺失、lint 没继承基础规则时，rulemason check 以非 0 退出，放进 CI 就能拦住。只有记录的版本号更旧、副本内容相同时，仍以 0 退出。

怎么工作

内置规则全程生效。有 key 才用 Jev；没有 key 时不调用 Jev。

  1. 内置规则

    全程生效

    • 九条写法
      外部操作与密钥
    • Python / React 落法
      界面文案三档，按项目复制
    • 方案写法、编码审慎
      产品产物审慎、文案卫生
      中文排版

  2. 方案

    1. /opsx:propose
      写方案

    2. 判断方案
      有 key 才用 Jev

    • 格式问题回到写方案。格式在本机检查，不调用 Jev。
    • 碰到红线停下问你。
    • 通过/opsx:apply 写代码前再查一次，有 key 才用 Jev。
    • 无 key不调用 Jev。格式在本机，其余待人工。--lint-only 只查格式。

  3. 写代码与自动检查

    1. 写代码

    2. 自动精简

    3. 独立审查

    4. ruff

    5. 测试

  4. 收尾归档

    1. 前端 lint

    2. 文案检查
      需开启判断；长文案有 key 才用 Jev

    3. 写检查记录
      verification.md

    4. /opsx:archive
      归档

  • 自动精简只动这次改动，需求、对外行为和接口保持不变。
  • 独立审查最多两轮。两轮后还有必须修的，就停下来说明。不把逐条审代码交给你。
  • 不走 OpenSpec 的小改动：项目有 openspec/ 时先读已写好的规格。会破坏已承诺的行为就先停下问你；不会就直接改，改完跑 ruff 和测试。这两种情况都不做自动精简和独立审查，也不写 verification.md。

用和不用，差在哪

不用 rulemason 用 rulemason
代码越写越多 重复、死代码、多余抽象慢慢堆积 每次写完先精简这次的改动，再交给独立审查者
规矩放在哪 CLAUDE.md、AGENTS.md 各写一份，手动同步 只在一处维护；每个工具读同一份只读副本，随项目提交
AI 说「写完了」 你自己跑 lint、跑测试、逐行审 ruff、测试、前端 lint 自动跑完，必须修的问题修好再审一遍
写代码之前 方案好不好全靠你看 开启判断后，方案写完、写代码前各查一次，碰到红线就停下等你
规矩被改了 没人发现 rulemason check 以非 0 退出，放进 CI 就能拦住
老项目接入 lint 一片红，无从下手 先建基线，之后只修每次改动新引入的问题

密钥与线上操作 看 AI 自觉 读可以直接做；改东西每次都要你同意；删除只给入口，由人操作；密钥不进对话

支持的工具

OpenSpec 的命令由 openspec init 生成，不同版本的文件名以它写出的为准。Claude Code 用冒号，Cursor 和 OpenCode 用连字符。Codex 只生成 skill，用 $ 加上 skill 名。

工具 读规矩的入口 /rulemason skill OpenSpec 命令
Claude Code CLAUDE.md（引用 AGENTS.md 和规矩副本） .claude/skills/rulemason/ /opsx:propose、/opsx:apply、/opsx:archive
Cursor AGENTS.md .agents/skills/rulemason/ /opsx-propose、/opsx-apply、/opsx-archive
Codex AGENTS.md .agents/skills/rulemason/ $openspec-propose、$openspec-apply-change、$openspec-archive-change
OpenCode opencode.jsonc 的 instructions .agents/skills/rulemason/（不在 / 列表里时，对它说「用 rulemason skill」） /opsx-propose、/opsx-apply、/opsx-archive

让你放心的设计

  • 先看清楚再写。init 和 remove 先列出要改哪些文件，确认后才写。update 会直接刷新它自己管的副本和入口；你的文件（ruff、ESLint、openspec/config.yaml 等）缺了配置时，先列出补齐计划，确认后才写。--plan 和 --dry-run 只看计划，什么都不写。
  • 不替你提交，不替你推送。写完的改动留在工作区，由你检查后提交。
  • 你的配置它不硬改。ruff 配置里写了 select、继承了项目外的配置、ESLint 写法认不出来时，只报告文件、行号、原文和改法。
  • 老项目不会一接入就炸。运行 /rulemason 先建基线，等你确认才写。之后关卡只修新引入的问题。不整条关掉规则，也不提高全局复杂度上限。
  • CI 能拦。规矩副本被改、工具入口缺失、lint 没继承基础规则时，rulemason check 以非 0 退出。只有记录的版本号更旧、副本内容相同时，仍以 0 退出。
  • 密钥不经过对话。rulemason key 在你自己的终端里输入，不显示，也不进命令历史，写在本机的 ~/.config/rulemason/env（POSIX 上权限 600），不进任何仓库。环境变量 TYPESAFE_API_KEY 优先于这个文件。
  • 随时能卸。rulemason remove --plan 先看会删什么，确认后再卸。你手改过、已经对不上记录的副本会留下并写在计划里。项目简介、红线和命令表留在 AGENTS.md 里。

常见问题

和自己手写一份 AGENTS.md 或 CLAUDE.md 有什么区别？

手写的规矩是一份提示词，AI 可能照做，也可能不照做；改了也没人知道。rulemason 多做了三件事：规矩在一处维护，每个工具读同一份副本；写完代码有固定的关卡；rulemason check 能在 CI 里发现副本被改或入口缺失。你自己的内容照样写在标记块外面。

和 OpenSpec 是什么关系？

OpenSpec 管「方案怎么写、怎么一步步落地」，rulemason 管「写的时候守什么规矩、写完要过哪些关」。rulemason 把方案写法规则补进 openspec/config.yaml，把关卡挂到 apply 和 archive 上。没有 OpenSpec 时，只接入规矩和 lint。

和 superpowers、get-shit-done（GSD）这类工作流插件冲突吗？

侧重点不同。它们主要管 AI 怎么规划和执行任务；rulemason 主要管代码和文档写成什么样、写完怎么检查，而且规矩随项目提交，CI 能查。

会不会改坏我的项目？

init 只写计划里列出的文件，不提交、不推送；改不了的 lint 配置只报告，不硬改。想先看看，用 rulemason init --plan。不想用了，用 rulemason remove --plan 先看会删什么。

要联网吗？要付费吗？

规矩、关卡、check、result-check 和 judge --lint-only 都在本机运行。只有开启 Jev 判断时才会联网调用 TypeSafe，key 在 typesafe.ai 申请。收费以该网站当时的说明为准。

不懂中文能用吗？

命令行输出、生成的规矩和 skill 都是中文。English 是这份说明的英文版；用的时候仍会看到中文输出。

能帮我申请软著或专利吗？

不能，它也不保证任何申请能通过。它能做的是让代码更精简、结构更清楚、注释到位，每次改动留有检查记录；整理申请材料时，这些都能省事。

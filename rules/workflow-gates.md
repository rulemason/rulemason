这些检查点包住每一次改代码，自动执行，无需提醒：走 OpenSpec 时按 change 的各个节点检查；不走 OpenSpec 的改动见「不走 OpenSpec 改代码时」，归档见「归档」。它们写在项目指令（AGENTS.md）引用的这份文件里，而不是工具生成的命令文件里，因为 `openspec update` 会覆盖那些文件。

下文的「命令表的〈名称〉」指项目指令里「本项目命令表」中名称相同的那一行；「红线规则」指命令表之后列出、供判断使用的实质类规则；「额外步骤」同理。「本项目」指被改文件往上最近的 `.rulemason.yaml` 所在目录，不是打开 AI 工具的目录，命令表、红线规则、额外步骤与主规格都按它取；一次改动涉及多个接入项目时，每个项目各跑一遍检查点：命令在该项目根执行，diff、审查材料与提交按项目分开。项目没有判断层时，见下文「没有判断层的项目」。

## 方案刚写完时

经 `/opsx:continue`、`/opsx:ff`、`/opsx:propose`，或在 explore 模式手写出 proposal / design 之后：

1. 运行命令表的「判断」。
2. 格式类 block（`lint/design`，含决策缺否决理由、Risks 格式、缺回滚说明；以及 `proposal-states-non-goals`）是起草失误：自己改好产物再跑一次。
3. 实质类 block 或 review（项目列出的红线规则，以及 `design-no-speculative-extension`）等于改方案：报告给用户决定，不自行修改。
4. 把最终结果（和改了什么）附在给用户的方案汇报里。

## apply 写任何代码之前

产物可能已被用户改过；用户已经看过，所以这里不静默修改。

1. 运行命令表的「判断」。
2. 任一 block：停下不碰代码，逐条报告规则与原文，等用户决定。
3. 只有 review：用一小段列出来，然后继续。

## apply 最后一个任务做完、汇报完成之前

按顺序：

1. 按下一节「自动精简与代码审查」，先精简本次改动，再独立审查；自动修复 block 与范围内可修的 review，并重新审查。
2. 运行命令表的「ruff」，修掉本次改动引入的问题（落在本次新增或修改的行上的问题、新加而未使用的 import，以及因本次改动在未改的行上新出现的问题，如函数变复杂后报在 `def` 行的 C901、插入 import 后报在块首的 I001、删掉定义后报在调用处的 F821）后重跑，直到这些问题消失。改动前就有的问题不修，汇报列出数量并建议运行 `/rulemason` 建立基线；搬动的旧代码带来的问题按既有问题处理，汇报写明。改到带「接入前遗留」豁免的文件时，清掉它的遗留豁免是可选的，汇报提一句。
3. 运行命令表的「测试」（不联网部分）；改动碰到既有测试时按「改既有测试时」一节处理；改了判断规则文件或 `JEV_MODEL` 时，加跑命令表的「判断回归」；命令表没有这一行时跳过，并在汇报中写明。
4. 改了前端时，运行命令表的「前端 lint」，修掉本次改动引入的问题（判断方法同第 2 步）后重跑，直到这些问题消失；改动前就有的问题不修，汇报列出数量并建议运行 `/rulemason` 建立 ESLint 基线。
5. 改了界面文案时，运行命令表的「文案检查」：block 必须修，review 列出。
6. 运行项目列出的额外步骤。
7. 写完成汇报：逐项写每一步的结果，含跳过了什么、为什么；对照 design 里各文件的估计行数，超出一倍的写明原因（没有 design 的最小 change 跳过这一项）。汇报写进 change 的 `verification.md`，再在对话里给出摘要。

## 自动精简与代码审查（apply 后）

上一节第 1 步的细则：先对本次 diff 执行行为保持的自动精简，再执行独立代码审查；整个过程不等待人工逐条审核。

**自动精简**只处理本次变更中的重复、死代码、冗余抽象或过复杂逻辑；本次新增的函数先按名字在仓库里检索，已有同名或同用途的实现就改为复用。精简必须保持需求、外部可观察行为与 API 不变，不得为减少行数重写无关代码；无法安全精简时保持原样并说明。

**独立审查**的审查者必须独立于实现者，只分析实现者提供的材料：工具能提供所有工具权限均拒绝的审查子代理时，材料放在交给它的消息里；否则用新会话、单独复审轮次，或只能读一份文件的子代理，由实现者把材料写成一份文件，审查者只读这份文件。审查者不读仓库其他文件、不运行命令、不修改文件。实现者必须提供本次 diff、未跟踪文件清单、change 产物及受影响测试 / 配置的相关内容，不得提供密钥、凭证或用户未提交的无关内容。材料不完整时，审查者报告缺少什么，由实现者筛选后补充。

审查范围：本次 diff 与未跟踪的新文件、change 的 proposal / design / tasks / specs、受影响的测试与配置的相关内容。输入中若意外包含敏感内容，只报告文件与位置，不引用或复制值。

检查项：

- **需求符合**：diff 覆盖 tasks / specs，没有范围外改动。
- **正确性**：边界、错误处理、返回值、回归风险。
- **安全**：密钥、注入、路径穿越、危险 shell、外部副作用。
- **代码质量**：九条、重复、复杂度、死代码、注释与命名。
- **测试**：新增行为有覆盖；现有测试在审查后的验证步骤运行，审查者检查覆盖是否充分。
- **变更卫生**：无无关文件、无调试输出、无注释掉的代码。

每项检查写 `pass`（通过且无发现），或列出 `block` / `review` 发现，附文件与行、原因和建议。`block` 和范围内可修的 `review` 由实现者自动修复，然后重新运行审查，最多两轮：

- 第二轮后仍有 block：停止实现，报告未消除项。
- 第二轮只剩 review：修复后跑完 ruff 与测试即可，不再审第三轮，修了什么写进汇报。
- 修复需要改变方案、规格或扩大范围时，才停下报告原因；不把逐条代码审核转交用户。

审查结果与修复摘要写进最终汇报。

## 改既有测试时

走不走 OpenSpec 都适用。有的测试读源码文件、再断言里面的某段原文；改代码碰到这类断言时：

- 只把断言改成新写法下的等价内容，不删除、不放宽，也不为了让断言通过把代码写成迎合测试的样子（如塞进测试截取的起止标记之间）。
- 汇报逐条列出改了哪些断言、改前改后各是什么。
- 确实写不出等价断言时停下说明，由用户决定。

## 不走 OpenSpec 改代码时

用户直接让你改代码、本次改动不属于任何进行中的 change 时，按下面做。项目没有 `openspec/` 时只做第 4 步。

1. **先读相关主规格**：用 `openspec list --specs` 看有哪些能力，用 `openspec show <能力> --type spec --json --no-scenarios` 找出与这次改动相关的一两份，再用 `openspec show <能力> --type spec` 完整读这几份（含场景）。只按能力名筛会漏：再把本次要改的测试函数名、路由路径与被改函数名在 `openspec/specs/` 里检索，命中的 requirement 一并读完、列进判路依据；要改既有测试的断言或白名单时先检索这个测试名，命中主规格点名的测试按「冲突」处理。
2. **判在哪条路**：
   - **改契约**：用户要的就是改变主规格已写的某条 requirement 或 scenario。代起一个最小 change：只写 proposal、规格增量与一两条 tasks，不写 design；按「方案刚写完时」跑判断后，用三五句话告诉用户要改主规格的哪一条，**停下等用户确认**。确认后按 apply 的各检查点做完，再按「归档」一节归档。
   - **冲突**：用户要的是别的事，但做法会顺带破坏主规格已写的某条 requirement 或 scenario。不改代码，指出会被破坏的那一条，问用户：换一个不破坏它的做法，还是把这条规格也改了（选改规格就按「改契约」走），或者放弃。选换做法时，按新做法重新判路。
   - **未覆盖**：主规格没写到这次要改的行为（样式、文案细节、内部实现等）。直接改，不补写规格；这个功能以后要成为对外承诺时，再走正常的 OpenSpec 流程。
   - **不改行为**：修 bug 让代码符合主规格、重构、改注释与文档。直接改。
3. **汇报写明依据**：读了哪几份主规格、哪几条 requirement，检索命中了什么（无命中也写），判在哪条路、为什么。判断错了，用户能一眼看出来并纠正。
4. **直接改完只跑 ruff 与测试**：不起 change 的直接改动（「未覆盖」「不改行为」两条路，以及项目没有 `openspec/` 时的任何改动）改完后，运行命令表的「ruff」与「测试」（不联网部分），改了前端时加跑「前端 lint」，碰到既有测试时按「改既有测试时」一节处理，修掉本次改动引入的问题后重跑，直到这些问题消失；改动前就有的问题不修，汇报列出数量并建议运行 `/rulemason` 建立基线，判断方法与遗留豁免的处理同「apply 最后一个任务做完」第 2 步。不跑自动精简与独立审查；不写 `verification.md`，结果写进给用户的汇报。

## 归档

一个 change 做完、用户要归档时（含上一节代起的最小 change）：

1. **自查**：tasks 全部勾完，change 目录里有 `verification.md`。不满足就不归档，说明还差什么。
2. **归档并入主规格**：运行 `openspec archive <change 名> --yes`，规格增量自动并入主规格。**不就「是否同步主规格」询问用户**：增量在方案阶段已经过用户确认。
3. **校验**：运行 `openspec validate --specs --strict`。
4. **失败时停下说明**：`openspec archive` 失败时什么都没移动，说明是哪条规格增量、为什么不合格、可以怎么改，修好后重新归档。归档已成功而校验失败时，change 已移进 `archive/`、主规格已合并，如实说明哪条主规格不合格、为什么，等用户决定用新 change 修正，还是授权你直接改主规格后再校验一次。两种情况都不自行跳过。
5. **判断层提示**：归档后运行 `rulemason check --json`。「判断」一行写着条件已满足、尚未启用，且 `facts` 里「已归档 change」正好是 3 或「接入后归档 change」正好是 1 时，在汇报末尾提示一次：「判断」一行含「本机未配置 key」就提示运行 `rulemason key` 配置，key 在 https://typesafe.ai/ 申请；已有 key 就提示在 AI 工具中运行 `/rulemason` 并说明要启用判断。两种说法都附一句：判断只审 OpenSpec 方案与界面文案。其余情况不提；不代用户配置 key，也不代为启用。

## 提交与推送

提交信息写成「类型(范围): 中文说明（change 名）」，类型取 `feat`、`fix`、`refactor`、`docs`、`chore` 之一，例如「feat(cli): 新增卸载命令（remove）」。归档提交写「chore: 归档 <change>，规格并入主 specs（…）」。与 change 无关的提交可以省略括号里的 change 名。项目配了 commitlint 时，按它的配置换行与限长。

同一工作区可能有别的会话或别人在提交：

- 提交只带本次计划内的文件，不把别人暂存的文件带进来。
- 共享分支上不用 amend，漏了文件就另开一个新提交补上。
- 推送前单独列出待推送的提交核对，和推送分两步；列表与预期不符时停下说明。
- 要并行开几个会话时，建议各用一个 `git worktree`，免得提交钩子临时收起未暂存改动时干扰对方。

## 没有判断层的项目

只执行「apply 最后一个任务做完」中不依赖 Jev 的步骤（自动精简、自动代码审查、ruff、测试、前端 lint、额外步骤）。文案检查依赖 Jev，汇报中写明「判断层未装」并跳过；方案刚写完与写代码前两个检查点同样不执行判断，「改契约」代起的最小 change 也一样。

## 可选：阶段学习文档同步 Notion

项目指令写明 Notion 落点页面才启用；没写就不启用，汇报中也不提。

启用后，每完成一个阶段（一个产物写完，或一段 apply 完成），主动在落点下新建下一篇编号子页，无需用户提醒。写给零基础读者：做了什么、为什么这样做、要敲的命令、应该看到什么；注明仓库是权威记录。

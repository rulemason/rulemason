# /rulemason 存量清理

文中的「第 1 节」「第 8 节」指同目录 `SKILL.md` 的章节；入口闸门见 `SKILL.md` 第 1 节与下文「入口」。

用户要清理既有代码时做：输入里带 `cleanup`，或自然语言说要做存量清理。不带模块名只诊断全仓；带模块名只修该模块。这是不改行为的重构，改完按检查点「不走 OpenSpec 改代码时」第 4 步跑 ruff、前端 lint 与测试。

**原则**：后文的做法按这七条与九条展开；后文没写到的情形，按这七条判断。

1. 别处按名字或原文依赖的东西不动（见 code-style 九条之外）。
2. 等价的证据要独立于「测试通过」；对跑测试写好后，先植入一处改动看它失败，看完还原，用 `git diff` 确认干净。
3. 指标是手段：指标变好而读者没得到好处，就放弃这一处。
4. lint 因重构要求改语义时（如要求改依赖数组），放弃这处重构，不去满足 lint。
5. 代理只改清单内的东西，行为差异逐项写进汇报。
6. 状态以 git 为准；笔记写明提交号。
7. 改前改后用同一条命令、同一组参数、同一个范围对比。

**入口**：先跑 `rulemason check --json`。`next.code` 为 `init`、`fix_manifest`、`upgrade_machine`、`update` 时按第 1 节停下，不诊断也不改文件。为 `fill_project_info`、`manual_lint`、`fix_gitignore`、`none` 时继续。可以继续时的展示按第 1 节，不贴全文。

**只诊断**：不带模块名时只输出诊断，不改任何文件。最后一行之前列出队列，不把队列写入文件。已有 `refactor(cleanup): <模块>` 提交的模块跳过。工作区干净的排在有未提交改动的前面；再按软指标条数从多到少，相同按行数从多到少，仍相同按模块路径字典序。高、中、低只标在行旁，不决定先后。潜力为低的合成一行，写明这次不做。还有工作区干净、且不是低的模块时，汇报最后一行写排序后第一条的 `/rulemason cleanup <模块>`。这条命令之前写一句这次要做的事，只用该模块已经抽到的 1 到 2 个例子，写明要动的位置、要做的事，以及哪一类软指标不算这次要清的内容。这句只给这一条命令点名的模块，不写入文件，也不代替进入后的计划，也不是用户确认。没有这种模块时，不写这句；在有未提交文件的模块里按同一顺序取第一条，最后一行写它的要先提交的路径，不进入该模块。这种模块也没有时，写明这次没有要做的模块。

模块算完成只认 `refactor(cleanup): <该模块>` 这种提交。清理改动还在工作区时仍算未完成。一个模块分几次提交时，只有最后一次用这个开头；之前的阶段提交写成 `refactor(cleanup-step): <模块> 第 N 步`，诊断不把它算完成。本 skill 不提交。

**诊断**分三层，每个模块都要有。只读代理同时最多 5 个；没有子代理就串行。不把诊断或进度写入 `.rulemason/` 或仓库里的新文件。

- 硬指标：读 ruff 与 ESLint 的「接入前遗留」条目和复杂度；前端函数复杂度用下文「复杂度探针」以 15 为阈值数个数与最大值。
- 机械软指标：在项目根跑一次 `ruff check --select ARG,ERA,BLE,S110,T201 --output-format json`，按文件归到模块后再按模块拆开计数（`--statistics` 没有路径，拆不开）。只加临时参数，不改项目的 lint 配置。查重复：有 Node 时 `npx --yes jscpd@5.4.2 <路径> --reporters json --output <仓库外临时目录>`，用完删掉；没有 Node 且有 Python 时 `uvx pylint@4.1.3 --disable=all --enable=duplicate-code <路径>`；没有可运行的工具、离线、下载失败或命令失败时，空出这一列并写明原因。缺首行注释单列：只报文件数，不计入软指标条数，不参与排序，也不算清理要做的事。
- 抽样：每个模块抽 2 到 3 个最大或最复杂的文件，读完给高、中、低三档精简潜力，并举 1 到 2 个例子；数出的重复份数写成「抽样所见，至少 N 份」。另列出被读源码断言钉住的文件：文件 → 读它的测试 → 钉住的片段。

进度不另存。硬指标看「接入前遗留」条目是否还在；软指标看 `git log --grep '^refactor(cleanup):'`。没有这种提交的模块，诊断里标明还没有清理提交。

**复杂度探针**：前端（JS、JSX、TS、TSX 与 HTML 内联脚本）的函数复杂度用本 skill 目录下的 `complexity-probe.mjs` 数，诊断、改前、改后用同一条命令与同一组参数。`<lint 目录>` 指项目前端 lint 运行的那一层，`<eslint>` 指从这里往上最近的 `node_modules/.bin/eslint`。

- 取清单：在 `<lint 目录>` 用项目自己的前端 lint 加 `--format json` 跑一次，取项目 lint 实际检查过的文件清单，换成相对于 `<lint 目录>` 的路径。只留 `.js` `.mjs` `.cjs` `.jsx` `.ts` `.tsx` `.mts` `.cts` `.html`，再去掉探针在标准错误里报「未测」的类型（TS 只认 `typescript-eslint` 这个包），以及在被测的那棵树里不存在的文件（如这次新建的文件，改前那棵树里还没有）；这次改名或删掉的文件，用 `git diff --name-status <改前提交>` 把旧路径补进改前清单。去掉的类型与文件在汇报里写明。
- 运行：在被测的那棵树里与 `<lint 目录>` 同一层的目录下运行 `PROBE_ROOT=<lint 目录> PROBE_MAX=<阈值> <eslint> -c <本 skill 目录>/complexity-probe.mjs <清单> --format json -o <仓库外临时文件>`。`PROBE_ROOT`、`<eslint>` 与 `-c` 都用主工作区里的绝对路径，在临时 worktree 里取改前数字时也一样，不在 worktree 里装依赖；不用 `npx eslint`，它会下载与项目不同的版本。
- 数结果：只数 `ruleId` 为 `complexity` 的条目，得出超过阈值的函数个数与最大值；有函数超标时退出码是 1，「找不到规则定义」、未用的 disable 注释这类条目也不算失败。结果的文件数要等于清单文件数，且没有解析失败、`File ignored`、`no matching configuration` 条目，否则这次数字不算，先查明原因。
- 空出这一列并写明原因：项目 ESLint 低于 9、没有 `node_modules`（如 Yarn PnP），或项目的 `complexity` 配了 `variant`。

**修一个模块**：模块名只划定范围，其他模块不改。先通读该模块的文件，列出软建议；再列出下面第 1、2 步的计划（分组、共用模块、要存的指标、准备落地的建议，以及分几步做、每步含哪些组，一次做完的写一步）。计划还要写：复杂度目标在「拆到下一档以内」与「当前上限留余量」中选一个，这批代码常与上游同步时选后者，写明理由；复杂度与行数分开预估，不承诺减行；逐个核对读源码测试截取用的锚点还在不在，找不到的报「过期锚点」；把读源码的断言改写成渲染断言只作可选前置步骤，须用户同意，按检查点「改既有测试时」逐条汇报改前改后；共用数据库等外部资源的测试由主会话统一跑，代理不各自跑。用户确认后再做，可以只同意其中几条；未确认不改任何文件。改文件的代理同时最多 3 个；没有子代理就串行。

1. **规划**：从 lint 的 JSON 输出或基线条目列出要清的文件，按模块分组，同一文件只属一组；清单里的文件有未提交改动时先剔除，或请用户先提交，否则改前提交对不上起点，`git diff` 核对也会混进用户的改动。每组建议 3–6 个文件。多组都要用的辅助函数先规划成共用模块、在一处建好，计划里写明各组复用它；不要为了缩小改动面要求「不新建文件」，那会让同一个函数在每组各复制一份。共用模块与第一个调用方放在同一步（用户按步提交），只建不用会违反九条第 9 条。
2. **先存证据**：动手前跑命令表的 ruff 或前端 lint（加 JSON 输出），统计要盯的指标（如超过 15 的函数个数与最大值，前端用「复杂度探针」）。清单文件与要跑的范围内都没有未提交改动时，直接在当前工作区取，并在证据里记下 `git status --short`；要盯重复数时，按本模块范围存一份基线。范围内有清单外的未提交改动，或动手之后才要补取改前数字时，在改前的提交上建一个临时 worktree（`git worktree add --detach <临时目录> <改前提交>`，临时目录放在仓库外，免得 lint 把它一起扫进去）再取；前端依赖先用本机缓存离线安装，缺的才下载；装不上时停下说明，由用户决定怎么取改前数字。不要把改前代码经 stdin 交给 lint：带类型检查的配置会按路径读磁盘上的当前文件，得到的是改后的数字。指标、代理汇报与分步计划写到仓库外的临时目录，写明提交号；它们不是进度，接着做之前先对照当前提交。必须放在仓库里的临时文件（如对跑测试）放在 lint 忽略、不入库的目录（`.gitignore` 已经忽略的目录，不为此改 `.gitignore`），这些文件不算诊断或进度，汇报写明基线提交号与复验方法。等价证据按原则 2 选做：纯函数对同一批输入比对改前改后的返回值；界面文案把改前改后的全部字符串按集合比对；对跑涉及当前时间时冻结时钟。
3. **代理指令**：每组同一份，按项目语言改写，并附上本文开头的七条原则。只改本组清单里的文件；共用数据库等外部资源的测试（主会话下发前列出）不跑，交主会话；需要对跑测试时写在主会话给出的目录里，按原则 2 植入、还原；不动 git 状态（不提交、不暂存、不切分支、不 stash）；行为等价是硬要求，React 按 react.md「重构等价性」逐条对照；碰到读源码断言原文的测试，按检查点「改既有测试时」处理；拆函数按计划选定的复杂度目标（主会话下发前填成具体档位），不刚好卡在上限；只能靠透传大量参数才能拆开的地方放弃，汇报写明位置与当前复杂度；不补首行注释。汇报写改了哪些文件、每个文件的指标改前改后，附一处有代表性的改前改后代码，以及等价性自查表（组件类型或位置、条件位置、求值时机、依赖数组、对象键序、默认值、副作用顺序，没有变化写「无」）；「被测试钉住」的结论附测试文件与行号，「没被钉住」的结论附检索用的命令。
4. **恢复**：有组中途停下（用量上限、出错）时，先用 `git diff --stat` 与清单核对哪些文件已经改完，只把没改完的交出去继续，不重做已完成的部分；证据文件不重跑。
5. **主会话复核**：在当前工作区重跑同样的指标（前端复杂度用同一条探针命令、同一份文件清单），与证据文件对比，要盯的指标都不应变差（如超过 15 的函数个数不应变多）；React 改动按「重构等价性」抽查；本次新增的函数按名字在仓库里检索，有重复就合并进共用模块。逐项看依赖数组变化、`eslint-disable` 增减与清单外文件；本轮新增文件里每个 `export` 都要有外部引用，没有就去掉；重复数用本模块的同一口径复核（只对该模块跑同一组参数）。分步做时，每步开工前对照当前提交核对清单。
6. **收尾**：清干净的文件从 ruff 或 ESLint 的「接入前遗留」条目里删掉，上限降一档的同步改配置；项目保留全局复杂度上限时，报告该范围实测超标个数与最高值。建过临时 worktree 的，用 `git worktree remove --force <临时目录>` 删掉（里面装过依赖，不加 `--force` 删不掉），再 `git worktree prune`；汇报按第 8 节写，附改前改后的指标对比。本 skill 不提交。计划分的几步（列计划时定的，不是这里 1–6 的流程编号）里还有没做完的时：请用户按 `refactor(cleanup-step): <模块> 第 N 步` 提交，一轮做完多步的每步各提交一次，不把该模块视为已完成，最后一行写继续该模块的 `/rulemason cleanup <模块>`，收尾到此为止。计划分的几步全部做完时：要让下次诊断认出这个模块，由用户提交，提交说明写成 `refactor(cleanup): <模块>`。收尾先要求这次提交。这一轮先排除当前模块，即使提交还没落地；之后不带模块名的诊断仍只认该提交。然后把该模块视为已完成，按同一顺序重算下一个：工作区干净的在前，再按软指标条数、行数从多到少、模块路径字典序。不再抽样，也不看高、中、低。还有工作区干净的未完成模块时，最后一行给出排序后第一条的 `/rulemason cleanup <模块>`，不改下一个模块的文件。同一次诊断的抽样里已有该模块的 1 到 2 个例子时，用那些例子在命令前再写一句这次要做的事，写明要动的位置、要做的事，以及哪一类软指标不算这次要清的内容。同一次诊断里没有这些例子时，不写这句，并写明具体改哪些等进入该模块后的计划。没有工作区干净的未完成模块时，在有未提交文件的模块里按软指标条数、行数、模块路径字典序取第一条，最后一行写它的要先提交的路径，不进入该模块；同一次诊断里没有该模块的例子时，写明具体改哪些等进入该模块后的计划。这种模块也没有时，只写明这次没有要做的模块，不写具体改哪些。这两种都不写这次要做的事。用户输入该命令后仍先列计划，用户确认后再做。
